# Phase 9: สิทธิ์ กฎหมาย จริยธรรม และความปลอดภัย

บทนี้เป็นแนวทางเชิงปฏิบัติสำหรับตัดสินใจก่อนเริ่ม Web Scraping จริง ไม่ใช่คำปรึกษาหรือคำรับรองทางกฎหมาย กฎของแต่ละประเทศ อุตสาหกรรม องค์กร และสัญญาอาจแตกต่างกัน ควรส่งกรณีที่มีความเสี่ยงให้เจ้าของข้อมูลและผู้เชี่ยวชาญที่เกี่ยวข้องตรวจสอบ

หลักสำคัญคือ **เข้าถึงเท่าที่ได้รับอนุญาต ใช้เท่าที่จำเป็น เก็บเท่าที่จำเป็น และหยุดทันทีเมื่อสิทธิ์หรือเงื่อนไขไม่ชัดเจน**

## 1. ตรวจช่องทางข้อมูลก่อน Scrape

เรียงลำดับการตัดสินใจดังนี้:

1. ตรวจ Official API หรือ Data Export ที่เจ้าของระบบจัดเตรียมไว้
2. อ่าน Terms of Service, API Terms, Privacy Policy และ Copyright Notice
3. ตรวจว่า URL และข้อมูลที่ต้องการอยู่ในขอบเขตที่ได้รับอนุญาตหรือไม่
4. ติดต่อเจ้าของเว็บไซต์เมื่อเงื่อนไขไม่ชัดเจน
5. เลือกใช้ข้อมูลสาธารณะหรือข้อมูลที่องค์กรมีสิทธิ์เข้าถึงเท่านั้น

การที่ข้อมูลเปิดดูได้ใน Browser ไม่ได้แปลว่าอนุญาตให้เก็บซ้ำ แจกจ่าย หรือใช้เชิงพาณิชย์ได้เสมอ

## 2. Terms, Copyright และการใช้ข้อมูล

- Terms of Service อาจกำหนดวิธีเข้าถึง ความถี่ การใช้งานต่อ และข้อห้ามของ Bot/Automation
- Copyright อาจคุ้มครองข้อความ รูปภาพ เอกสาร โค้ด และฐานข้อมูล แม้ URL จะเป็นสาธารณะ
- การเก็บข้อมูลเพื่อวิเคราะห์ภายในอาจมีความเสี่ยงต่างจากการเผยแพร่ซ้ำหรือขายต่อ
- บันทึก URL, วันที่ตรวจ Terms, เวอร์ชันเอกสาร และผู้อนุมัติไว้ใน project record
- อย่าคัดลอกเนื้อหามากเกินวัตถุประสงค์ และอย่าเอาข้อมูลที่มีเงื่อนไขห้ามเผยแพร่เข้า Repository

## 3. Privacy และ Personal Data

จัดประเภทข้อมูลก่อนเขียน Extractor:

| ประเภท | ตัวอย่างการตัดสินใจ |
| --- | --- |
| Public non-personal | ใช้ได้เมื่อ Terms และวัตถุประสงค์อนุญาต แต่ยังต้องเคารพ Rate Limit |
| Personal data | หลีกเลี่ยงก่อน ถ้าจำเป็นต้องมีฐานสิทธิ์ วัตถุประสงค์ และ retention ที่ชัดเจน |
| Sensitive/high-risk | หยุดและส่งให้ผู้รับผิดชอบ Privacy/Security อนุมัติก่อน |
| Secret/authentication data | ห้ามเก็บจากเว็บไซต์หรือ commit ลง Git; ใช้ Secret Manager ตามนโยบายองค์กร |

แนวทาง Data Minimization:

- ดึงเฉพาะ field ที่ตอบโจทย์ ไม่ดึงทั้งหน้าโดยไม่จำเป็น
- ตัดชื่อผู้ใช้ อีเมล เบอร์โทร ที่อยู่ และ identifier ที่ไม่จำเป็นออกตั้งแต่ชั้น Parse
- Mask หรือ hash identifier เมื่อไม่จำเป็นต้องรู้ค่าจริง
- ไม่ใช้ข้อมูลเพื่อวัตถุประสงค์ใหม่โดยไม่มีการตรวจสิทธิ์ใหม่

## 4. Authentication และ Access Control

- ต้องมีบัญชีและสิทธิ์ที่ได้รับอนุญาตก่อนเข้าข้อมูลที่ไม่ใช่ Public
- ใช้บัญชี Service Account ที่มีสิทธิ์ต่ำสุดและมีเจ้าของรับผิดชอบ
- ห้ามเดา Password, ข้าม Login, ขโมย Cookie/Token หรือใช้ Session ของผู้อื่น
- `401` และ `403` คือสัญญาณให้หยุดตรวจสิทธิ์ ไม่ใช่สัญญาณให้เพิ่ม Retry
- ห้ามทดสอบ endpoint ที่ไม่ได้รับอนุญาต แม้จะมองเห็นจาก Developer Tools

## 5. robots.txt, Rate Limit และภาระต่อ Server

`robots.txt` เป็นสัญญาณสำคัญเกี่ยวกับเส้นทางที่เจ้าของเว็บต้องการให้ Crawler เข้าถึง แต่ไม่ใช่ใบอนุญาตแทน Terms หรือสัญญา และไม่ใช่ข้อยกเว้นให้ข้าม Access Control

ก่อนส่ง Request ให้กำหนด:

- User-Agent ที่ระบุวัตถุประสงค์อย่างเหมาะสมและช่องทางติดต่อเมื่อจำเป็น
- Rate Limit และ concurrency ต่ำเท่าที่เพียงพอ
- Timeout, retry ที่มีเพดาน และ backoff แบบเพิ่มระยะ
- การหยุดเมื่อได้รับ `401`, `403`, `429` หรือสัญญาณผิดปกติ
- ช่วงเวลาทำงานที่ลดผลกระทบต่อระบบ เมื่อเจ้าของข้อมูลกำหนดไว้

อย่าเปลี่ยน User-Agent, IP, Header หรือพฤติกรรมเพื่อหลบระบบป้องกัน Bot และอย่าส่ง Request ซ้ำโดยไม่มีขอบเขต

## 6. Retention, Deletion และความปลอดภัย

กำหนดก่อนเริ่มงาน:

- เก็บข้อมูลอะไรและเก็บไว้นานเท่าใด
- Raw data, Processed data, Log และ Screenshot อยู่ที่ใด
- ใครเข้าถึงได้และต้องใช้สิทธิ์ระดับใด
- วิธีลบข้อมูลเมื่อหมดวัตถุประสงค์หรือได้รับคำขอให้ลบ
- วิธีตรวจว่าไฟล์สำรองและ temporary files ถูกลบด้วย

ห้ามใส่ Token, Cookie, Password, Personal Data หรือไฟล์ที่ได้จากระบบจริงใน Git ตัวอย่างควรใช้ Local Mock Website และข้อมูลสังเคราะห์

## 7. Incident Stop Rule

หยุดงานและแจ้งผู้รับผิดชอบทันทีเมื่อพบอย่างใดอย่างหนึ่ง:

- ได้รับ `401`, `403`, `429` หรือหน้าแจ้งห้าม Automation
- พบ CAPTCHA, Login ที่ไม่มีสิทธิ์ หรือ Access Control ที่ไม่คาดหมาย
- Response มี Personal Data/Secret เกินกว่าขอบเขตที่อนุมัติ
- Request rate สูงผิดปกติ, Server error เพิ่มขึ้น หรือระบบเริ่มช้าลง
- Terms/Privacy/เจ้าของข้อมูลเปลี่ยนแปลง
- ไม่สามารถอธิบายได้ว่าข้อมูลมีสิทธิ์ใช้ต่ออย่างไร

เมื่อหยุดแล้ว ให้เก็บเฉพาะ metadata ที่จำเป็น เช่น เวลา URL ที่ปลอดภัย status และ error class อย่าเก็บ payload ลับเพื่อการ debug โดยอัตโนมัติ

## Pre-scraping Checklist

```text
[ ] มี Official API หรือ Export ที่เหมาะสมหรือไม่
[ ] อ่าน Terms of Service, API Terms และ Privacy Policy แล้วหรือยัง
[ ] ตรวจ Copyright และข้อจำกัดการใช้/เผยแพร่แล้วหรือยัง
[ ] แหล่งข้อมูลและวัตถุประสงค์ได้รับอนุญาตหรือไม่
[ ] ข้อมูลเป็น Public, Personal, Sensitive หรือ Secret ประเภทใด
[ ] ต้อง Login หรือใช้ Authentication หรือไม่ และมีสิทธิ์หรือไม่
[ ] มี Access Control, CAPTCHA หรือ Bot Protection หรือไม่
[ ] ตรวจ robots.txt และข้อกำหนด Crawler แล้วหรือยัง
[ ] กำหนด User-Agent, Rate Limit, Timeout และ Retry budget แล้วหรือยัง
[ ] กำหนด field ที่จำเป็นและวิธีลด/Mask Personal Data แล้วหรือยัง
[ ] กำหนด Retention, Access Control และวิธีลบข้อมูลแล้วหรือยัง
[ ] กำหนด Stop Rule และผู้รับผิดชอบเมื่อเกิด Incident แล้วหรือยัง
[ ] ยืนยันว่าไม่มี Secret หรือข้อมูลจริงอยู่ใน Repository/Log หรือยัง
[ ] มีการบันทึกผู้อนุมัติ วันที่ตรวจ และหลักฐานการตัดสินใจหรือยัง
```

## เกณฑ์ตัดสินใจ

ถ้าคำตอบของข้อสิทธิ์, วัตถุประสงค์, Personal Data, Authentication หรือ Stop Rule ยังไม่ชัดเจน ให้ถือว่า **ยังไม่พร้อมเริ่ม Scrape** และหยุดไว้ก่อนจนกว่าจะได้รับคำตอบหรือการอนุมัติที่เหมาะสม

หลังจบ Phase 9 ให้หยุดและทบทวน Checklist ก่อนดำเนินการ Phase ถัดไป
